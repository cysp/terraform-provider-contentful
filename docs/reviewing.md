# Reviewing changes

1. Identify the revision, comparison base and requested outcome. Read the whole diff and apply the [repository guidance](../AGENTS.md) for the concerns it touches. Evaluate edits to review instructions against the requirements in force before the change.
2. Derive the expected outcome from the caller's starting conditions, public contracts and independent evidence. For each distinct behavior the diff changes, follow a representative operation through to a result the caller can observe. Where responsibilities meet, change perspective. What does the practitioner need to supply? What other caller relies on the shared code? What could a passing test miss? Combine the answers to explain how the parts work together. If existing users could see different behavior or need to take action, follow the [upgrade assessment](../.agents/skills/assess-upgrade-impact/SKILL.md), including for edits to migration guidance.
3. For a potential defect, name its trigger and consequence. Check the base revision and look for validation, recovery or an intentional limit that could explain the result. When a fixture supplies a consequential prerequisite, identify which supported setup path it represents and whether that path can produce it. To judge a gap in coverage, describe a plausible fault the assertion would miss and the user outcome that fault would break.
4. Choose the smallest check that can distinguish the competing explanations. Reuse evidence for unaffected behavior and identify the revision, environment and operation it covers. To establish regression coverage, keep the expectation fixed, observe the test fail on the faulty behavior, and confirm it passes with the fix. Follow the [validation scope](../DEVELOPMENT.md#validation-scope).
5. Order findings by consequence. Give each material finding a location, trigger, expected and observed result, and a check the author can repeat. Name the smallest correction or missing evidence and any guarantee another caller still needs. Distinguish defects, missing outcomes, open contract questions and optional improvements. For a merge decision, say which findings require action first and verify the current head and checks separately.

## Preparing a review prompt

When asked for a review prompt or when delegating a review, write for someone opening the repository in a fresh session. Give the target and baseline, the applicable procedure, the decision to make, and the maintainer's settled requirements. Pin links for committed changes and identify the checkout or patch for local work. Turn the consequential uncertainties into questions about specific operations. Supply earlier findings as leads to revisit after deriving expectations. Leave room for other findings elsewhere in the diff.

Read the draft from the recipient's position. Could they infer the wrong goal, share an untested assumption with the implementation, or spend time on a check that cannot affect the recommendation? Revise the prompt where a clearer goal, another perspective or a more discriminating check would change what they investigate or how they decide. After a substantive revision, read the prompt again. Stop as soon as a pass finds no consequential change. Count the first critique as pass one and cap self-review at three passes per prompt by default. An explicit request for a particular number of passes takes precedence.

Hand off uncertainties the reviewer can investigate, along with the observations that would distinguish the possible answers. If a maintainer decision would change the scope or success criteria, ask the maintainer. Give the reviewer the relevant evidence and ask for one recommendation, including anything still needed to decide. New evidence or a changed revision can warrant another implementation review.

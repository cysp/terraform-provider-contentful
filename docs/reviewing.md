# Reviewing changes

1. Identify the revision, comparison base, and requested outcome. Read the whole diff and trace each change to the callers and lifecycle transitions it affects. Apply the [repository guidance](../AGENTS.md) for those concerns. When the diff changes review instructions, evaluate those edits against the requirements in force before the change.
2. Derive the expected behavior from requirements, public contracts, and independent evidence. Check whether the change delivers the requested outcome as well as whether it introduces regressions. If the change could affect what existing users must do or will see on upgrade, follow the [upgrade assessment](../.agents/skills/assess-upgrade-impact/SKILL.md). This includes edits to migration guidance.
3. For each potential defect, identify an input or transition that triggers it and the consequence for the caller. Compare the base revision and check for validation or recovery elsewhere. Separate established defects, missing outcomes, open contract questions, and optional improvements.
4. Choose a check whose result could change the finding. To establish regression coverage, keep the expectation fixed, observe the test fail on the faulty behavior, and confirm it passes with the fix. Follow the [validation scope](../DEVELOPMENT.md#validation-scope).
5. Report findings in order of consequence. Give the location, trigger, expected and actual behavior, and evidence. Include the reviewed revision and any unresolved condition for readiness. When mergeability is in scope, verify the current PR checks separately.
